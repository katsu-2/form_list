# フォーム営業自動化ツール + リスト作成ツール 開発プラン

## 1. 概要

企業サイトの問い合わせフォーム経由で営業メッセージを送付する「フォーム営業」を効率化するツール群を開発する。

- **リスト作成ツール**: 営業対象となる企業リスト(企業名・URL・問い合わせフォームURL 等)を収集・管理する
- **フォーム営業ツール**: リストをもとに問い合わせフォームへメッセージを入力・送信し、結果を記録する

2つは独立したモジュールとしつつ、共通のDBを介して連携する。

## 2. 設計上の基本方針(コンプライアンス)

自動化にあたり、以下を仕様として組み込む。これはツールの信頼性・継続利用のための必須要件とする。

1. **営業お断りサイトの除外**: フォームページに「営業目的の送信禁止」等の文言を検出した場合は自動でスキップし、理由を記録する
2. **CAPTCHA は回避しない**: reCAPTCHA 等を検出したら自動送信せず「手動対応キュー」に回す
3. **送信レート制限**: 同一ドメインへの連続送信禁止、全体でも送信間隔(例: 30秒〜)と1日あたりの上限を設ける
4. **NGリスト管理**: 一度断られた企業・ドメインは永続的に除外
5. **送信前確認モード**: 初期は「下書き生成→人が確認→送信」の半自動をデフォルトとし、完全自動は明示的なオプトインにする
6. **送信ログの完全保存**: いつ・どこへ・何を送ったかを全件記録(スクリーンショット含む)

## 3. 技術スタック(推奨)

| 領域 | 技術 | 理由 |
|---|---|---|
| 言語 | Python 3.12 | スクレイピング・自動化ライブラリが充実 |
| ブラウザ自動化 | Playwright | フォーム検出・入力・送信、SPA対応、スクリーンショット |
| Web UI / API | FastAPI + Jinja2(または Streamlit で簡易に) | リスト管理・送信キュー操作用の管理画面 |
| DB | SQLite(MVP)→ PostgreSQL(スケール時) | 単一ユーザーならSQLiteで十分 |
| ジョブ実行 | APScheduler(MVP)→ Celery + Redis(スケール時) | 送信ジョブのキュー・レート制御 |
| フォーム項目マッピング | ルールベース + LLM(Claude API)補助 | 多様なフォームのフィールド推定 |

## 5. データモデル(主要テーブル)

- **companies**: id, 企業名, 法人番号, ドメイン, サイトURL, 業種, 所在地, 収集元, ステータス
- **contact_forms**: id, company_id, フォームURL, フィールドマッピング(JSON), CAPTCHA有無, 営業禁止文言フラグ, 最終検証日時
- **templates**: id, 名前, 件名, 本文(変数 `{{company_name}}` 等を埋め込み可)
- **campaigns**: id, 名前, template_id, 対象リスト条件, 送信モード(半自動/自動), レート設定, ステータス
- **send_logs**: id, campaign_id, company_id, 送信日時, 結果(成功/失敗/スキップ/手動待ち), 失敗理由, スクリーンショットパス
- **ng_list**: ドメイン/企業ID, 登録理由, 登録日時

## 6. モジュール別仕様

### 6.1 リスト作成ツール

**収集ソース(優先順)**
1. **国税庁 法人番号システム Web-API**(無料・公式): 法人名・所在地の一次データ
2. **手動インポート**: CSV/スプレッドシートからの取り込み(既存リスト活用)
3. **業種別ディレクトリ・検索エンジン経由の収集**: キーワード×地域で企業サイトURLを収集(robots.txt を尊重)

**処理パイプライン**
```
収集 → 正規化(社名表記ゆれ・ドメイン抽出) → 重複排除 → NGリスト照合
     → フォームURL探索(/contact, /inquiry 等の候補パス + サイト内リンク解析)
     → フォーム解析(フィールド構造・CAPTCHA・営業禁止文言の検出)
     → DB保存 / CSVエクスポート
```

**フォームURL探索ロジック**
- 典型パス(`/contact`, `/inquiry`, `/form`, `/お問い合わせ` 等)を優先試行
- トップページのリンクテキスト(「お問い合わせ」「CONTACT」)を解析
- 見つからない場合は「フォームなし」として記録

### 6.2 フォーム営業ツール

**フォーム解析(フィールドマッピング)**
1. ルールベース: `name`/`id`/`label`/`placeholder` 属性から「会社名」「氏名」「メール」「電話」「本文」を推定(日英キーワード辞書)
2. 推定できない項目は LLM に HTML を渡してマッピングを補完
3. マッピング結果は contact_forms に保存し再利用(2回目以降は解析不要)

**送信フロー**
```
キャンペーン開始
  → 対象企業を抽出(NG・送信済み・営業禁止を除外)
  → テンプレートに変数を差し込み下書き生成
  → [半自動モード] 管理画面で人が確認・承認
  → Playwright でフォームへ入力
  → 確認画面があれば「送信」まで遷移(確認画面パターンの検出)
  → 完了画面の判定(サンクスページ・完了文言) + スクリーンショット保存
  → send_logs に記録
```

**エラー/例外ハンドリング**
- CAPTCHA検出 → 手動対応キューへ
- 必須項目のマッピング不能 → 手動対応キューへ
- 送信失敗(タイムアウト・バリデーションエラー)→ リトライ1回 → 失敗記録

### 6.3 管理画面

- リスト一覧(検索・フィルタ・CSV入出力)
- テンプレート編集(変数プレビュー付き)
- キャンペーン作成・進捗ダッシュボード(送信数/成功率/スキップ理由内訳)
- 手動対応キュー(CAPTCHA等で止まった案件を人が処理)
- NGリスト管理

## 9. 主なリスクと対策

| リスク | 対策 |
|---|---|
| フォーム構造が多様でマッピング失敗 | ルールベース+LLM補完、失敗時は手動キューに逃がす設計 |
| 誤送信(内容・宛先ミス) | 半自動モードをデフォルト、送信前プレビュー必須、全件スクリーンショット |
| 送信先からのクレーム | NGリスト即時反映、営業禁止文言の自動検出、レート制限 |
| CAPTCHA の普及で自動送信率低下 | 回避はせず手動キュー化。手動処理の効率化UIでカバー |
| スクレイピングのブロック | robots.txt 尊重、アクセス間隔制御、User-Agent 明示 |
